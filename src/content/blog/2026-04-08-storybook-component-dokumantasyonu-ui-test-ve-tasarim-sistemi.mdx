# Storybook Rehberi: Component Dokümantasyonu, UI Test ve Tasarım Sistemi

Storybook, modern yazılım geliştirme ekosisteminde **izole component geliştirme ve UI dokümantasyonu** için kullanılan önemli başlıklardan biridir. Bu yazı, Storybook konusunu yalnızca tanım seviyesinde değil; mimari karar, üretim ortamı, performans, güvenlik, test ve ekip ölçeği açısından ele alır.

Bu rehber özellikle tasarım sistemi ve component library geliştiren frontend ekipleri için hazırlandı. Amaç, yazıyı okuyan kişinin Storybook hakkında temel kavramları öğrenmesi, gerçek projede hangi kararları vereceğini anlaması ve hangi hatalardan kaçınacağını bilmesidir.

## Kısa Tanım

Storybook, tek başına bir araç veya kütüphane olarak düşünülmemelidir. Asıl değeri, yazılım sistemindeki sorumluluğu doğru konumlandırıldığında ortaya çıkar. Bir teknolojinin iyi seçilmiş olması, kodun sadece bugün çalışması değil, yarın değiştirilebilir, gözlemlenebilir ve güvenli kalması anlamına gelir.

Güçlü görüşüm şu: **Storybook kullanımı, popülerlikten çok problem alanı ve ekip olgunluğu üzerinden değerlendirilmelidir.** Yanlış bağlamda seçilen iyi teknoloji bile teknik borç üretir. Doğru bağlamda seçilen teknoloji ise ekip hızını artırır ve sistem karmaşıklığını kontrol altında tutar.

## Mimari Bakış Açısı

Storybook kullanılan frontend mimarisinde temel amaç, ekran bazlı dağınık kod yerine yetenek bazlı modüller üretmektir. Component, state, veri çekme, validation, erişilebilirlik ve test sorumlulukları ayrıldığında hem kullanıcı deneyimi hem de geliştirme hızı iyileşir.

Mimari karar verirken şu sorular erken sorulmalıdır:

1. Bu teknoloji sistemin hangi katmanında sorumluluk alıyor?
2. Değişim maliyeti hangi ekibe ve hangi kod alanına yansıyacak?
3. Test, gözlemlenebilirlik ve güvenlik bu kararın neresinde duruyor?
4. Bu seçim ölçekleme ihtiyacı doğduğunda kolaylık mı sağlayacak, yoksa yeni bir kısıt mı oluşturacak?
5. Ekip bu teknolojiyi sadece kullanabiliyor mu, yoksa debug edip işletebiliyor mu?

## Örnek Kullanım

Aşağıdaki örnek, Storybook için temel yaklaşımı göstermek amacıyla sade tutulmuştur. Production ortamında validation, hata yönetimi, güvenlik, logging ve test katmanları ayrıca ele alınmalıdır.

```tsx
import type { Meta, StoryObj } from "@storybook/react";
import { Button } from "./Button";

const meta = { component: Button, args: { children: "Kaydet" } } satisfies Meta<typeof Button>;
export default meta;

export const Primary: StoryObj<typeof meta> = { args: { variant: "primary" } };
```

Bu örnek bir başlangıç noktasıdır. İyi production kodu; tip güvenliği, gözlemlenebilirlik, geri dönüş stratejisi ve hata davranışıyla birlikte düşünülmelidir.

## Production Best Practices

- **Konfigürasyon** Konfigürasyon ve secret yönetimini koddan ayırın.
- **Hata** Hata formatı, log standardı ve izleme metriklerini baştan belirleyin.
- **CI/CD** CI/CD içinde test, lint, type-check ve security scan adımlarını çalıştırın.
- **Rollback** Rollback stratejisini deploy stratejisinin parçası yapın.
- **Dokümantasyon** Dokümantasyon ve mimari karar kayıtlarını kısa ama güncel tutun.
- **Bundle** Bundle analizi yapın ve kritik render yolunu ölçün.
- **Erişilebilirlik** Erişilebilirlik kontrollerini tasarım sisteminin parçası hâline getirin.

## Performans ve Ölçekleme

Storybook performansı ölçülürken tek bir metriğe bakmak yeterli değildir. Ortalama değerler çoğu zaman yanıltıcıdır; P95/P99 gecikme, hata oranı, kaynak tüketimi, kuyruk birikimi, cache davranışı ve kullanıcıya yansıyan deneyim birlikte değerlendirilmelidir.

Ölçekleme kararı verilmeden önce darboğaz belirlenmelidir. Sorun CPU mu, ağ mı, veri modeli mi, yanlış cache stratejisi mi, yoksa gereksiz senkron bağımlılıklar mı? Bu soruya cevap vermeden yapılan optimizasyon genellikle maliyeti artırır ama problemi çözmez.

## Güvenlik ve Bakım

Storybook kullanılan sistemlerde güvenlik sonradan eklenen bir eklenti gibi düşünülmemelidir. Input validation, permission kontrolü, secret yönetimi, dependency taraması, log hijyeni ve audit ihtiyacı tasarımın parçası olmalıdır.

Bakım tarafında ise şu yaklaşım etkilidir:

- Major versiyon yükseltmeleri küçük parçalara bölünmelidir.
- Kritik bağımlılıklar için sahiplik belirlenmelidir.
- Deprecated API kullanımı CI aşamasında yakalanmalıdır.
- Incident sonrası aksiyonlar backlog’da kaybolmamalı, iyileştirme planına dönüşmelidir.
- Dokümantasyon, sadece kurulum notu değil karar nedeni de içermelidir.

## Test Stratejisi

Storybook için test stratejisi, riskli davranışları güvence altına almalıdır. Her şeyi test etmek mümkün değildir; bu yüzden en kritik kullanıcı akışları, veri dönüşümleri, hata senaryoları ve entegrasyon sınırları önceliklendirilmelidir.

İyi test stratejisi şu dengeyi kurar:

- Unit test ile saf iş mantığı hızlı doğrulanır.
- Integration test ile dış bağımlılık sınırları kontrol edilir.
- E2E test ile kritik kullanıcı akışı güvenceye alınır.
- Contract test ile servisler arası beklenti kırılmaları erken yakalanır.
