## Kısa Tanım

## Mimari Bakış Açısı

Fastify kullanılan bir sistemde ilk karar, sınırların nasıl çizileceğidir. Kod tabanı küçükken her şey aynı klasörde yaşayabilir; ancak büyüyen sistemlerde şu sorulara erken cevap verilmelidir:

1. Domain mantığı nerede duracak?
2. Dış dünya ile iletişim hangi katmandan geçecek?
3. Test edilebilirlik için bağımlılıklar nasıl izole edilecek?
4. Hata yönetimi merkezi mi, dağıtık mı olacak?
5. Gözlemlenebilirlik hangi seviyede başlatılacak?

Fastify ile backend geliştirirken controller/handler katmanı ince tutulmalı, domain kuralları servis veya use-case katmanında yaşamalıdır. Transport protokolü değişse bile iş kurallarının değişmemesi iyi bir mimari sinyalidir.

İyi mimari, teknolojiyi görünmez kılar. Kullanıcılar Fastify kullandığınızı bilmez; sadece sistemin hızlı, güvenilir ve tutarlı çalıştığını hisseder. Geliştiriciler ise teknolojinin sunduğu soyutlamalar sayesinde yeni özellikleri daha düşük riskle ekler.

## Örnek Kullanım

Aşağıdaki örnek, Fastify için temel yaklaşımı göstermek amacıyla sade tutulmuştur. Gerçek projede validation, hata yönetimi, logging, test ve güvenlik katmanları ayrıca eklenmelidir.

```ts
import Fastify from "fastify";

const app = Fastify({ logger: true });

app.get("/users/:id", {
  schema: {
    params: {
      type: "object",
      required: ["id"],
      properties: { id: { type: "string" } },
    },
  },
}, async (request) => {
  return { id: (request.params as { id: string }).id };
});

await app.listen({ port: 3000 });
```

Bu örneği production kodu gibi düşünmeyin; bunu zihinsel model olarak düşünün. İyi örnek kod, teknolojinin hangi problemi çözdüğünü gösterir. Production kodu ise o problemi güvenlik, performans, bakım ve ekip süreçleriyle birlikte çözer.

## Üretim Ortamı İçin En İyi Pratikler

Fastify production ortamına taşındığında aşağıdaki pratikler kritik hâle gelir:

- **Konfigürasyonu koddan ayırın.** Ortam değişkenleri, secret yönetimi ve deploy konfigürasyonu açıkça ayrılmalıdır.
- **Hata yönetimini standartlaştırın.** Her hata aynı formatta loglanmalı, izlenmeli ve mümkünse kullanıcıya kontrollü cevap dönmelidir.
- **Test stratejisi kurun.** Unit test, integration test ve kritik akışlar için e2e test seviyelerini netleştirin.
- **Gözlemlenebilirliği baştan ekleyin.** Log, metric ve trace sonradan eklenince genellikle eksik kalır.
- **Performansı ölçmeden optimize etmeyin.** Tahminle yapılan optimizasyonlar çoğu zaman yanlış katmanı iyileştirir.
- **Dokümantasyon yazın.** Teknoloji kararının nedeni, sınırları ve alternatifleri ADR formatında saklanmalıdır.
- **Versiyon yükseltmeyi süreç hâline getirin.** Bağımlılıkları yıllarca sabit bırakmak kısa vadede rahat, uzun vadede pahalıdır.

## Sık Yapılan Hatalar

- **schema kullanmamak**: schema kullanmamak kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **plugin sınırlarını yanlış kurmak**: plugin sınırlarını yanlış kurmak kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **hata formatını standartlaştırmamak**: hata formatını standartlaştırmamak kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **request log correlation eksikliği**: request log correlation eksikliği kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.

Bu hatalar genellikle teknoloji kötü olduğu için değil, bağlam yanlış kurulduğu için ortaya çıkar. Fastify iyi bir araç olabilir; fakat her aracı aynı problem için kullanmaya çalışmak mimariyi kırılganlaştırır.

## Ölçekleme ve Performans

Performans yalnızca hız demek değildir. Performans; doğru kaynak kullanımı, tahmin edilebilir gecikme, stabil throughput ve kullanıcı deneyimi demektir. Fastify ile çalışırken performansı şu metriklerle değerlendirmek gerekir:

- Ortalama yanıt süresi
- P95/P99 gecikme
- Hata oranı
- Kaynak kullanımı
- Soğuk başlangıç veya ilk yükleme maliyeti
- Cache hit/miss oranı
- Kullanıcı deneyimine yansıyan metrikler

Fastify performansında latency, throughput, bağlantı yönetimi, veritabanı sorguları ve serialization maliyeti birlikte ölçülmelidir. Tek endpoint hızlı olsa bile sistem geneli yavaş olabilir.

Ölçekleme kararı almadan önce darboğazı ölçmek gerekir. Kod mu yavaş, veritabanı mı zorlanıyor, ağ gecikmesi mi yüksek, yoksa yanlış cache stratejisi mi var? Bu soruya cevap vermeden yapılan yatay ölçekleme çoğu zaman maliyeti artırır ama problemi çözmez.

## Güvenlik ve Bakım

Fastify projelerinde güvenlik, framework veya araç seçimiyle otomatik çözülmez. Güvenlik bir süreçtir. Kimlik doğrulama, yetkilendirme, input validation, secret yönetimi, dependency taraması ve log hijyeni birlikte ele alınmalıdır.

Bakım tarafında ise şu yaklaşım güçlüdür:

- Her kritik bağımlılık için owner belirleyin.
- Major versiyon yükseltmelerini küçük parçalara bölün.
- Deprecated API kullanımını CI içinde yakalayın.
- Test kapsamını sadece oran olarak değil, risk alanı olarak takip edin.
- Incident sonrası teknik borçları backlog'a değil, doğrudan iyileştirme planına alın.
