## Mimari Bakış Açısı

Next.js kullanılan bir sistemde ilk karar, sınırların nasıl çizileceğidir. Kod tabanı küçükken her şey aynı klasörde yaşayabilir; ancak büyüyen sistemlerde şu sorulara erken cevap verilmelidir:

1. Domain mantığı nerede duracak?
2. Dış dünya ile iletişim hangi katmandan geçecek?
3. Test edilebilirlik için bağımlılıklar nasıl izole edilecek?
4. Hata yönetimi merkezi mi, dağıtık mı olacak?
5. Gözlemlenebilirlik hangi seviyede başlatılacak?

Next.js tarafında mimariyi ekranlardan değil, tekrar kullanılabilir yeteneklerden başlatmak gerekir. UI bileşenleri domain modelini yutmamalı; veri çekme, state yönetimi, erişilebilirlik ve tasarım sistemi ayrı sorumluluklar olarak ele alınmalıdır.

İyi mimari, teknolojiyi görünmez kılar. Kullanıcılar Next.js kullandığınızı bilmez; sadece sistemin hızlı, güvenilir ve tutarlı çalıştığını hisseder. Geliştiriciler ise teknolojinin sunduğu soyutlamalar sayesinde yeni özellikleri daha düşük riskle ekler.

## Örnek Kullanım

Aşağıdaki örnek, Next.js için temel yaklaşımı göstermek amacıyla sade tutulmuştur. Gerçek projede validation, hata yönetimi, logging, test ve güvenlik katmanları ayrıca eklenmelidir.

```tsx
// app/blog/[slug]/page.tsx
import { notFound } from "next/navigation";

export async function generateMetadata({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPostBySlug(slug);

  return {
    title: post?.title ?? "Yazı bulunamadı",
    description: post?.excerpt,
    alternates: { canonical: `/blog/${slug}` },
  };
}

export default async function BlogPostPage({ params }: { params: Promise<{ slug: string }> }) {
  const { slug } = await params;
  const post = await getPostBySlug(slug);
  if (!post) notFound();

  return <article>{post.content}</article>;
}
```

Bu örneği production kodu gibi düşünmeyin; bunu zihinsel model olarak düşünün. İyi örnek kod, teknolojinin hangi problemi çözdüğünü gösterir. Production kodu ise o problemi güvenlik, performans, bakım ve ekip süreçleriyle birlikte çözer.

## Üretim Ortamı İçin En İyi Pratikler

Next.js production ortamına taşındığında aşağıdaki pratikler kritik hâle gelir:

- **Konfigürasyonu koddan ayırın.** Ortam değişkenleri, secret yönetimi ve deploy konfigürasyonu açıkça ayrılmalıdır.
- **Hata yönetimini standartlaştırın.** Her hata aynı formatta loglanmalı, izlenmeli ve mümkünse kullanıcıya kontrollü cevap dönmelidir.
- **Test stratejisi kurun.** Unit test, integration test ve kritik akışlar için e2e test seviyelerini netleştirin.
- **Gözlemlenebilirliği baştan ekleyin.** Log, metric ve trace sonradan eklenince genellikle eksik kalır.
- **Performansı ölçmeden optimize etmeyin.** Tahminle yapılan optimizasyonlar çoğu zaman yanlış katmanı iyileştirir.
- **Dokümantasyon yazın.** Teknoloji kararının nedeni, sınırları ve alternatifleri ADR formatında saklanmalıdır.
- **Versiyon yükseltmeyi süreç hâline getirin.** Bağımlılıkları yıllarca sabit bırakmak kısa vadede rahat, uzun vadede pahalıdır.

## Sık Yapılan Hatalar

- **gereksiz client component kullanımı**: gereksiz client component kullanımı kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **cache davranışını varsaymak**: cache davranışını varsaymak kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **metadata üretimini ihmal etmek**: metadata üretimini ihmal etmek kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.
- **route handler içinde domain sınırlarını bozmak**: route handler içinde domain sınırlarını bozmak kısa vadede hızlı görünür; fakat büyüyen projelerde debug maliyetini ve değişiklik riskini artırır.

Bu hatalar genellikle teknoloji kötü olduğu için değil, bağlam yanlış kurulduğu için ortaya çıkar. Next.js iyi bir araç olabilir; fakat her aracı aynı problem için kullanmaya çalışmak mimariyi kırılganlaştırır.

## Ölçekleme ve Performans

Performans yalnızca hız demek değildir. Performans; doğru kaynak kullanımı, tahmin edilebilir gecikme, stabil throughput ve kullanıcı deneyimi demektir. Next.js ile çalışırken performansı şu metriklerle değerlendirmek gerekir:

- Ortalama yanıt süresi
- P95/P99 gecikme
- Hata oranı
- Kaynak kullanımı
- Soğuk başlangıç veya ilk yükleme maliyeti
- Cache hit/miss oranı
- Kullanıcı deneyimine yansıyan metrikler

Next.js performansında render maliyeti, bundle boyutu, cache, lazy loading ve kullanıcı etkileşim süresi birlikte değerlendirilmelidir. Özellikle kullanıcıya görünen ilk anlamlı içerik ve etkileşim gecikmesi kritik metriklerdir.

Ölçekleme kararı almadan önce darboğazı ölçmek gerekir. Kod mu yavaş, veritabanı mı zorlanıyor, ağ gecikmesi mi yüksek, yoksa yanlış cache stratejisi mi var? Bu soruya cevap vermeden yapılan yatay ölçekleme çoğu zaman maliyeti artırır ama problemi çözmez.

## Güvenlik ve Bakım

Next.js projelerinde güvenlik, framework veya araç seçimiyle otomatik çözülmez. Güvenlik bir süreçtir. Kimlik doğrulama, yetkilendirme, input validation, secret yönetimi, dependency taraması ve log hijyeni birlikte ele alınmalıdır.

Bakım tarafında ise şu yaklaşım güçlüdür:

- Her kritik bağımlılık için owner belirleyin.
- Major versiyon yükseltmelerini küçük parçalara bölün.
- Deprecated API kullanımını CI içinde yakalayın.
- Test kapsamını sadece oran olarak değil, risk alanı olarak takip edin.
- Incident sonrası teknik borçları backlog'a değil, doğrudan iyileştirme planına alın.
