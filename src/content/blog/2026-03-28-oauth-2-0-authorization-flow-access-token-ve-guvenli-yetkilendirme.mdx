# OAuth 2.0 Rehberi: Authorization Flow, Access Token ve Güvenli Yetkilendirme

## Mimari Bakış Açısı

OAuth 2.0 güvenlik mimarisinde tek başına yeterli değildir; token yaşam döngüsü, session stratejisi, yetkilendirme modeli, audit log ve secret yönetimi birlikte ele alınmalıdır.

Mimari karar verirken şu sorular erken sorulmalıdır:

3. Test, gözlemlenebilirlik ve güvenlik bu kararın neresinde duruyor?

5. Ekip bu teknolojiyi sadece kullanabiliyor mu, yoksa debug edip işletebiliyor mu?

## Örnek Kullanım

Aşağıdaki örnek, OAuth 2.0 için temel yaklaşımı göstermek amacıyla sade tutulmuştur. Production ortamında validation, hata yönetimi, güvenlik, logging ve test katmanları ayrıca ele alınmalıdır.

```txt
1. Client kullanıcıyı authorization server’a yönlendirir.
2. Kullanıcı izin verir ve authorization code döner.
3. Client code + PKCE verifier ile token alır.
4. API çağrılarında access token kullanılır.
```

Bu örnek bir başlangıç noktasıdır. İyi production kodu; tip güvenliği, gözlemlenebilirlik, geri dönüş stratejisi ve hata davranışıyla birlikte düşünülmelidir.

## Performans ve Ölçekleme

OAuth 2.0 performansı ölçülürken tek bir metriğe bakmak yeterli değildir. Ortalama değerler çoğu zaman yanıltıcıdır; P95/P99 gecikme, hata oranı, kaynak tüketimi, kuyruk birikimi, cache davranışı ve kullanıcıya yansıyan deneyim birlikte değerlendirilmelidir.

Ölçekleme kararı verilmeden önce darboğaz belirlenmelidir. Sorun CPU mu, ağ mı, veri modeli mi, yanlış cache stratejisi mi, yoksa gereksiz senkron bağımlılıklar mı? Bu soruya cevap vermeden yapılan optimizasyon genellikle maliyeti artırır ama problemi çözmez.

## Güvenlik ve Bakım

OAuth 2.0 kullanılan sistemlerde güvenlik sonradan eklenen bir eklenti gibi düşünülmemelidir. Input validation, permission kontrolü, secret yönetimi, dependency taraması, log hijyeni ve audit ihtiyacı tasarımın parçası olmalıdır.

Bakım tarafında ise şu yaklaşım etkilidir:

- Major versiyon yükseltmeleri küçük parçalara bölünmelidir.
- Kritik bağımlılıklar için sahiplik belirlenmelidir.
- Deprecated API kullanımı CI aşamasında yakalanmalıdır.
- Incident sonrası aksiyonlar backlog’da kaybolmamalı, iyileştirme planına dönüşmelidir.
- Dokümantasyon, sadece kurulum notu değil karar nedeni de içermelidir.

## Test Stratejisi

OAuth 2.0 için test stratejisi, riskli davranışları güvence altına almalıdır. Her şeyi test etmek mümkün değildir; bu yüzden en kritik kullanıcı akışları, veri dönüşümleri, hata senaryoları ve entegrasyon sınırları önceliklendirilmelidir.

İyi test stratejisi şu dengeyi kurar:

- Integration test ile dış bağımlılık sınırları kontrol edilir.
- E2E test ile kritik kullanıcı akışı güvenceye alınır.
- Contract test ile servisler arası beklenti kırılmaları erken yakalanır.
