# OpenAPI Rehberi: REST API Sözleşmesi, Schema, Client Generation ve Governance

OpenAPI, modern yazılım geliştirme ekosisteminde **REST API için makine tarafından okunabilir sözleşme standardı** için kullanılan önemli başlıklardan biridir. Bu yazı, OpenAPI konusunu yalnızca tanım seviyesinde değil; mimari karar, üretim ortamı, performans, güvenlik, test ve ekip ölçeği açısından ele alır.

Bu rehber özellikle public/internal API geliştiren backend ve platform ekipleri için hazırlandı. Amaç, yazıyı okuyan kişinin OpenAPI hakkında temel kavramları öğrenmesi, gerçek projede hangi kararları vereceğini anlaması ve hangi hatalardan kaçınacağını bilmesidir.

## Kısa Tanım

OpenAPI, tek başına bir araç veya kütüphane olarak düşünülmemelidir. Asıl değeri, yazılım sistemindeki sorumluluğu doğru konumlandırıldığında ortaya çıkar. ## Mimari Bakış Açısı

OpenAPI backend tarafında konumlandığında transport katmanı ile domain katmanı ayrılmalıdır. HTTP, GraphQL, gRPC veya realtime protokol değişebilir; fakat iş kuralları bu değişimlerden minimum etkilenmelidir.

Mimari karar verirken şu sorular erken sorulmalıdır:

1. Bu teknoloji sistemin hangi katmanında sorumluluk alıyor?
2. Değişim maliyeti hangi ekibe ve hangi kod alanına yansıyacak?
3. Test, gözlemlenebilirlik ve güvenlik bu kararın neresinde duruyor?
4. Bu seçim ölçekleme ihtiyacı doğduğunda kolaylık mı sağlayacak, yoksa yeni bir kısıt mı oluşturacak?
5. Ekip bu teknolojiyi sadece kullanabiliyor mu, yoksa debug edip işletebiliyor mu?

## Örnek Kullanım

Aşağıdaki örnek, OpenAPI için temel yaklaşımı göstermek amacıyla sade tutulmuştur. Production ortamında validation, hata yönetimi, güvenlik, logging ve test katmanları ayrıca ele alınmalıdır.

```yaml
openapi: 3.1.0
info:
  title: Coreor API
  version: 1.0.0
paths:
  /users/{id}:
    get:
      operationId: getUser
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        "200":
          description: User found
```

Bu örnek bir başlangıç noktasıdır. İyi production kodu; tip güvenliği, gözlemlenebilirlik, geri dönüş stratejisi ve hata davranışıyla birlikte düşünülmelidir.

## Production Best Practices

- **Konfigürasyon** Konfigürasyon ve secret yönetimini koddan ayırın.
- **Hata** Hata formatı, log standardı ve izleme metriklerini baştan belirleyin.
- **CI/CD** CI/CD içinde test, lint, type-check ve security scan adımlarını çalıştırın.
- **Rollback** Rollback stratejisini deploy stratejisinin parçası yapın.
- **Dokümantasyon** Dokümantasyon ve mimari karar kayıtlarını kısa ama güncel tutun.
- **Timeout,** Timeout, retry, rate limit ve idempotency politikalarını açıkça tanımlayın.
- **Database** Database ve dış servis çağrılarını trace edilebilir yapın.

Bu hataların çoğu teknolojinin kendisinden değil, teknolojinin yanlış sınıra yerleştirilmesinden kaynaklanır. OpenAPI güçlü bir araç olabilir; fakat her güçlü araç gibi yanlış kullanıldığında sistemin karmaşıklığını artırır.

## Performans ve Ölçekleme

OpenAPI performansı ölçülürken tek bir metriğe bakmak yeterli değildir. Ortalama değerler çoğu zaman yanıltıcıdır; P95/P99 gecikme, hata oranı, kaynak tüketimi, kuyruk birikimi, cache davranışı ve kullanıcıya yansıyan deneyim birlikte değerlendirilmelidir.

Ölçekleme kararı verilmeden önce darboğaz belirlenmelidir. Sorun CPU mu, ağ mı, veri modeli mi, yanlış cache stratejisi mi, yoksa gereksiz senkron bağımlılıklar mı? Bu soruya cevap vermeden yapılan optimizasyon genellikle maliyeti artırır ama problemi çözmez.

## Güvenlik ve Bakım

OpenAPI kullanılan sistemlerde güvenlik sonradan eklenen bir eklenti gibi düşünülmemelidir. Input validation, permission kontrolü, secret yönetimi, dependency taraması, log hijyeni ve audit ihtiyacı tasarımın parçası olmalıdır.

Bakım tarafında ise şu yaklaşım etkilidir:

- Major versiyon yükseltmeleri küçük parçalara bölünmelidir.
- Kritik bağımlılıklar için sahiplik belirlenmelidir.
- Deprecated API kullanımı CI aşamasında yakalanmalıdır.
- Incident sonrası aksiyonlar backlog’da kaybolmamalı, iyileştirme planına dönüşmelidir.
- Dokümantasyon, sadece kurulum notu değil karar nedeni de içermelidir.

## Test Stratejisi

OpenAPI için test stratejisi, riskli davranışları güvence altına almalıdır. Her şeyi test etmek mümkün değildir; bu yüzden en kritik kullanıcı akışları, veri dönüşümleri, hata senaryoları ve entegrasyon sınırları önceliklendirilmelidir.

İyi test stratejisi şu dengeyi kurar:

- Unit test ile saf iş mantığı hızlı doğrulanır.
- Integration test ile dış bağımlılık sınırları kontrol edilir.
- E2E test ile kritik kullanıcı akışı güvenceye alınır.
- Contract test ile servisler arası beklenti kırılmaları erken yakalanır.
